# 策略验证、回测可信度与实盘安全五阶段设计

日期：2026-07-27  
状态：已获用户原则批准，待按本文复核后实施

## 1. 背景与目标

当前 `full-version` 分支已经补齐原开源版计划中的 M0–M7 功能，并通过现有离线测试；策略研究侧已经形成 `freeze_v4`、`S1bz`、`S2py10`、conviction、z-limit 与 z-exit 等候选组件。不过研究代码和大部分产物位于仓库外的 `C:\chanpy\research`，回测执行口径仍有已知乐观偏差，策略信号与实盘配置也未完全接通。

本设计的目标不是继续无约束寻找参数，而是建立一条可以审计、复现和安全演练的交付链：

1. 将现有研究过程工程化并锁定可复现基线；
2. 修正影响结论可信度的回测执行语义；
3. 在修正后的口径下重新认证 v5；
4. 使认证策略能够安全进入 dry-run/testnet 演练；
5. 完成全量验收、文档和实盘前检查。

## 2. 硬性边界

- 阶段严格串行；当前阶段验收失败时，不进入下一阶段。
- 不在阶段 3 最终候选形成前读取或运行新的 2026 OOS 策略结果。
- 已公开的 `freeze_v4` 2026 结果只作为历史记录，不用于继续调参。
- 默认禁止真实下单。阶段 4 只运行单元测试、dry-run 和用户明确配置的 testnet；任何 live 模式必须显式解锁。
- 不把约 1 GB 行情数据、pickle 缓存或密钥提交到 Git。仓库只保存代码、小型规范化结果、数据清单与哈希。
- 不引入新的第三方依赖；优先使用标准库和项目现有依赖。
- `freeze_v4` 历史指标保持可追溯；新执行语义产生的新指标使用新的口径版本，不静默覆盖旧结果。

## 3. 总体架构

### 3.1 单一研究入口

在仓库内建立轻量研究包，负责配置解析、数据清单、交易记录规范化、门槛判定和报告生成。外置目录继续承载大数据和一次性历史素材，但不再作为唯一可执行源。

研究命令采用显式输入：数据根目录、时间范围、策略配置、执行口径和输出目录。路径不得写死为某台机器的绝对路径。每份结果包含：

- Git commit 与工作区状态；
- 策略配置及其规范化哈希；
- 数据文件范围、行数、时间边界和哈希；
- Python/关键库版本；
- 执行口径版本；
- 随机种子（如适用）；
- 指标、门槛结论和失败原因。

本地 pickle 只作为受信任的迁移输入；进入正式验证链前转换为有 schema 版本的 JSON/JSONL，不在验证器内直接加载未知 pickle。

### 3.2 双口径回测

保留 `legacy-v1` 口径用于复现既有 `freeze_v4` 记录；新增 `conservative-v2` 作为 v5 认证口径。两者结果不可混写或直接比较而不标明口径。

`conservative-v2` 至少包含：

- 权益曲线按可用行情逐根盯市，最大回撤不再只看已平仓权益；
- 同一根 K 线同时触发入场和止损时采用对策略不利的确定性顺序；
- maker 限价必须实际触及，成交价格不优于委托价，并保留未成交结果；
- 手续费区分 maker/taker，z-limit 排除金字塔加仓腿；
- 永续合约在持仓跨越结算时计入资金费；
- 并发、总杠杆、单笔杠杆和风险预算在事件发生时统一检查；
- 缺少验证所需 OHLC/资金费数据时显式失败，不回退到乐观默认值。

真实数据勘验发现，2021–2025 的 BTC 小时线包含 8 段、合计 29 根缺失 K 线，最长连续缺失 15 根；受影响区间前后报价连续，但有历史持仓跨越其中 3 段。为避免把“没有可用行情”误写成任意成交价，`conservative-v2` 仅在盯市层使用预登记的 `carry_forward`：以最后可用收盘价生成带 `synthetic=true` 的盯市点，连续缺失上限为 16 根，并在报告中逐段披露。合成点不得用于限价触及、追价、止损或其他成交判断；超过上限、缺少资金费或成交所需真实 K 线时仍显式失败。

### 3.3 策略认证门槛

阶段 3 只认证一个预先登记的 v5 候选：

`S1bz + S2py10 + conviction#14 + z-limit(S2 非加仓腿) + z-exit`

认证顺序固定为：

1. BTC 2021–2025 全期及 A/B/C 分段；
2. ETH/SOL/BNB 同参数多品种门槛；
3. 多品种组合层风险与回撤；
4. 所有 IS 门槛通过后，才允许一次预登记的 2026 OOS 评估。

门槛值从现有研究日志抽成机器可读规则，报告同时展示基线、候选、差值与通过原因。任何阶段失败都输出正式失败报告，不在同一轮根据 OOS 结果改参数。

### 3.4 实盘信号与订单边界

认证策略通过一个版本化配置对象同时供回测和交易端读取，避免 `StaticsChanConfig.py` 另有一套参数。信号对象必须携带策略版本、模型分数、风险倍率、止损和委托意图；缺字段时拒绝开仓。

订单生命周期改为显式状态机：

`signal -> submitted -> partially_filled -> open -> closing -> closed/canceled/rejected`

核心原则：

- 下单返回 `open` 或零成交时不得把计划数量记为已开仓；
- 部分成交只记录实际成交量和加权均价；
- 开仓和平仓在途订单都能轮询与重启恢复；
- 平仓单携带 `reduceOnly`，maker 意图携带 `postOnly`；
- 现货余额与合约持仓使用不同查询路径；
- 单向/双向持仓、杠杆和 `positionSide` 由显式配置决定；
- dry-run 模拟保证余额、持仓和订单状态约束与真实接口一致，禁止无约束负持仓掩盖空头语义问题；
- live 模式除 API 密钥外还要求显式环境开关，默认 fail-closed。

## 4. 串行阶段与验收

### 阶段 1：研究工程化与可复现基线

工作内容：

- 盘点外置研究脚本，迁移正式验证所需的最小代码；
- 建立版本化配置、交易记录 schema、数据清单和统一 CLI；
- 将现有 v4/v5 IS 小型结果转换为规范化产物；
- 清理硬编码路径，记录外置数据的时间边界与哈希；
- 为配置哈希、schema、数据边界、报告稳定性和 OOS 防护补测试。

完成标准：在不读取 2026 候选结果的前提下，一条命令可复现 2021–2025 基线报告；相同输入得到字节稳定或语义稳定的结果；缺数据、越过时间边界或配置漂移时明确失败。

### 阶段 2：提升回测可信度

工作内容：

- 用测试锁定现有 `legacy-v1` 行为；
- 实现 `conservative-v2` 的逐根盯市、同 K 线不利顺序、maker 成交、费用和资金费；
- 增加合成行情场景，覆盖长/短仓、跳空、同柱多事件和多持仓组合；
- 生成 v4 在新旧口径下的差异报告，解释差异来源。

完成标准：所有执行规则均有最小反例测试；旧报告可复现；新口径不依赖隐式乐观回退；差异能够分解到回撤、成交、费用或资金费。

### 阶段 3：重新认证 v5

工作内容：

- 冻结候选配置和门槛规则；
- 依次运行 BTC、ETH、SOL、BNB 与组合层 IS；
- 若 IS 全部通过，执行唯一一次预登记的 2026 OOS；
- 输出 `candidate`、`rejected` 或 `insufficient-data` 结论，不包装失败结果。

完成标准：报告包含完整 provenance、逐门槛证据和执行口径；所有结果可从规范化输入重建；只有 IS 全过才产生 OOS 结果和正式 v5 冻结文件。

### 阶段 4：完善实盘安全性

工作内容：

- 回测/交易共用认证策略配置；
- 贯通模型分数和风险字段；
- 扩展数据库与订单状态机以支持开仓在途、部分成交和幂等恢复；
- 为 CCXT 接入 post-only、reduce-only、合约持仓、杠杆和持仓模式；
- 强化 dry-run，并用模拟交易所测试异常、撤单重下和重启恢复。

完成标准：任何未确认成交不得形成开放持仓；部分成交和重启不重复下单；合约多空语义明确；无显式 live 解锁时不可能触达真实下单分支。

### 阶段 5：最终验收与交付

工作内容：

- 运行离线全量测试、针对性集成测试、静态语法检查和 dry-run 演练；
- 更新 `README_FULL.md`、`CLAUDE.md`、`STRATEGY_LOG.md`；
- 记录环境、命令、结果、已知限制和剩余风险；
- 形成实盘前检查表，明确 testnet 与 live 仍需的外部验证。

完成标准：仓库状态可审计；测试结果与文档数字一致；策略报告明确标注数据截止日和口径；不存在已知的静默成交、仓位或 OOS 泄漏问题。真实交易仍保持锁定。

## 5. 测试策略

所有行为变更遵循测试优先：先写失败测试，再做最小实现。

- 单元测试：配置/schema、门槛比较、费用、资金费、盯市、状态转移；
- 属性/参数化测试：长短仓对称、费用单调性、较差成交不应改善收益、未成交不产生持仓；
- 回归测试：`legacy-v1` 指标、v4 规范化报告、现有 M0–M7 测试；
- 集成测试：临时 SQLite + 假交易所，覆盖提交、部分成交、撤单、平仓和恢复；
- 端到端测试：外置数据只读输入到最终报告，以及信号到 dry-run 完整闭环；
- 网络测试默认隔离，不能作为离线验收的必要条件。

## 6. 错误处理与审计

- 研究命令遇到 schema、哈希、时间边界或配置不一致时返回非零状态，并生成结构化错误；
- 每个门槛结论保留输入与规则版本，不允许只写“通过/失败”；
- 交易状态转换使用幂等数据库操作，非法转换立即拒绝；
- 交易所返回未知状态时保留在途并告警，不猜测成交；
- 密钥、完整账户响应和敏感配置不得写入报告或日志。

## 7. 明确不做

- 不在本轮探索新的策略族或继续参数挖掘；
- 不把历史 scratch 脚本全部搬入仓库；
- 不承诺旧历史指标在 `conservative-v2` 下保持不变；
- 不连接真实资金账户，不替用户完成 live 授权；
- 不因 v5 未通过而修改门槛或反复使用 OOS。
